## Controlled drill procedure

Use invented inputs only. Do not introduce real private data to test the boundary.
The in-session handling role is limited to the published assignment; a responsible
reviewer must inspect the actual resulting reports and handling.

| Case | Action and required observation | Current result |
| --- | --- | --- |
| Bug intake | Use the published Apple bug route with exact public source/build context, invented reproduction, expected/observed result and no attachments. Record the actual created issue, delivery mechanism and the Apple triage response with its next step | Unexecuted |
| Evidence correction and wrong-category recovery | Submit a public synthetic-example correction, retain its synthetic label, then exercise routing correction on the same report. Record the actual category, canonical review boundary and preserved version/conditions | Unexecuted |
| Diagnostic redaction preview | Prepare a synthetic local preview containing an excluded marker, remove it before submission, read the complete final preview and verify the actual delivered body omits it. The published receipt must identify only safe fixture data and exact final content | Unexecuted |
| Cancellation or unavailable route | Stop before submission or observe the actual route failure; confirm no claimed report delivery and preserve local report text. Retry explicitly after recovery and record the resulting ticket only if it exists | Unexecuted |
| Confidential request | Verify that public guidance sends no confidential details to a public form and supplies no invented private inbox or response promise. Actual private delivery cannot be accepted until its destination and receiver are verified | Source boundary prepared; private delivery unverified |

A source/YAML check establishes the prepared configuration only. An API-created
controlled fixture may establish its own exact delivery and routing, but cannot
be labelled an exercised GitHub form, installed browser journey or private intake.
Each observed mechanism, failed attempt and recovery must retain its real source
and date. A screenshot of a form alone cannot satisfy the required ticket.

## Review and remaining limits

The guide requires review of the complete final diagnostic metadata and any
attachment before manual submission. It does not implement automated secret
detection, an app diagnostic exporter or a private upload service. GitHub permits
later free-text edits and attachments; the app cannot sanitize those later inputs.

No ongoing human support rota, service-level commitment, private/security
destination, live service authority or installed-device qualification is inferred.
The existing shared evidence, pricing, contracts and source-use review authorities
remain unchanged. Current public routes and limited in-session handling can be
qualified independently while those remaining outcomes stay explicit.

Do not close #122 from source publication or green code checks alone. Reconcile
the literal criteria against the real tickets, safe handling/recovery observations,
exact accepted versions and independent receiving review. Preserve unresolved
confidential-intake and operating responsibilities in that disposition.
