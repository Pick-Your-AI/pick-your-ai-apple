## Actual basis, answer identity and source qualification

`CapacityBasis` accepts one complete original frozen BuildSnapshot, an exact
operation, named original input byte buffers and the selected catalog input name.
It uses the existing mandatory Build decoder and schema checks. The retained
build ID, revision, locks, selection IDs and actual directed links are never
filled from another graph. The selected catalog snapshot is fully validated,
including unused items and exact item/version uniqueness. A missing locked
catalog or version stays unresolved; there is no ID-only fallback.

The framed basis digest covers every named input's name, kind and exact bytes,
the original Build bytes, the selected operation/catalog, and the named
normalization/source policies. Input ordering does not alter identity. Changing
only whitespace, an engine/hardware input, a qualifier input or the operation
invalidates a dependent result even if build ID and revision remain equal.
A hash proves identity; it does not establish eligibility or authority.

`CapacityAnswerIndex` admits only the closed CD1-0.2 envelope and validates every
record before requested-field consumption. It retains original bytes/hash,
`provided`, `unknown`, `missing`, `withheld` and `not_applicable`, the original
provided `assumption` Boolean, optional original `preset:` source, requested
pointer and actual source pointer. Ancestor and withheld-descendant causes remain
distinct. Exact UTF-8 keys and pointer components prevent canonical-equivalence
collapse. Duplicate/overlapping pointers, future versions, malformed unused
records and unselected fields reject.

`CapacityAnswers` reads an actual named answers input from the basis. The fixed
16-field vocabulary covers Boolean/text/set values, ByteCount, original positive
integer tokens, placement/residency/reserve labels, complete runtime bindings,
quantity traces and attribution-related enums. It is not an arbitrary schema
evaluator. ByteCount is a canonical ASCII decimal string, including `"0"`;
booleans, numeric JSON values, exponents and leading zeros are not ByteCount.
Positive count fields retain integer-token identity: `1.0` and `1e0` remain
floating tokens and are explicitly outside that selected consumer field even
when the canonical JSON Schema integer check accepts their mathematical values.

Each `CapacityQualification` binds one real answer, its original basis/input/hash,
requested field/path, fact and exact domain to an actual retained qualification
or source-policy input. Constructor admission checks every supplied qualification,
including unused entries. The caller must explicitly supply qualified
eligibility and a resolved conflict/rank assessment. Missing, ineligible or
unresolved evidence cannot become qualified because of a matching digest,
preset label or checked-only tag.

Each check retains the observations and qualification uses on which it depends.
Checked-only evidence remains checked-only through adapter lineage, inherited
responsibility and the early opaque-provider memory skip. An unrelated unused
qualification does not turn into measured evidence. Automatic descriptions and
error codes omit original IDs, values, URLs and source contents; explicit
properties retain them for an authorized caller. This API is not a sharing or
diagnostic-sanitization boundary.

## Serving graph, lineage and responsibility

`CapacityGraph` resolves role meanings only on actual Build edges and for the
selected operation. Required host/engine/device/base bindings, optional absence,
wrong kinds, disabled targets, missing versions, ambiguity and incomplete
coverage have distinct outcomes. Multiple candidates never choose an array-order
winner. An explicit adapter follows only its actual base edge, qualified kind and
base requirement, exact catalog base reference and qualified base version. A full
or merged artifact keeps its own serving graph.

The cycle regression uses an explicitly synthetic two-adapter catalog/Build
carrier to exercise bounded client traversal. It does not claim an approved real
catalog cycle, bypass canonical producer semantics, or adopt a second graph.
Visited exact selection identities terminate traversal with an unresolved result.

`CapacityDeployment` derives responsibility per enabled serving component.
Self-hosted components retain local requirements. Provider-shared, reserved or
dedicated capacity remains scoped to the actual effective artifact. Qualified
opaque exposure can make local hardware inapplicable while remote capacity
remains unknown. Missing capacity mode or exposure cannot justify an API-only
classification or suppress another local vector database. Service/artifact
support failures and required-role failures remain independent of a memory sum.

## Physical pools, allocations and workload

`CapacityMemory` receives explicit device instances, physical pools, consumers,
allocations, scenarios, independent limits and separate completeness claims.
Provided references, duplicate identities, physical aliases, reciprocal pool
membership and scenario rows are admitted before any skipped/unknown result.
A pool's complete address-space, partition and tenancy identity is required.
An array of devices or an advertised capacity sum cannot establish one pool.

A shared allocation is charged once only when its actual extent, non-overlap,
consumer set, normalization and scenario residency are qualified. Two real copies
are two charges. Host offload and simultaneously resident staging buffers belong
to their actual pools. Consumer/runtime access is a separate check; passing a
byte inequality does not prove access, runtime support or measured fit.

Byte sums use exact decimal arithmetic. For a before-reserve budget, qualified
upper demand plus qualified upper reserve is compared with qualified lower
capacity. An after-reserve budget already excludes the reserve, which is retained
as provenance and not charged again. Explicit qualified zero capacity is valid
for this profile; zero demand can pass and one byte cannot. Missing bounds,
weights-only coverage, unknown physical identity and incomplete lifetimes remain
unknown. A qualified independent excess survives an unresolved additional
nonnegative term when its disjoint identity and residency remain established.

Conservative mode requires one all-resident scenario. Selected exclusive
on-demand scenarios require explicit lifetime, charge, exhaustiveness and
transition evidence; they do not sum unrelated stage maxima or assume mutual
exclusion. Always-resident components and retained allocations remain in every
applicable lifetime. Per-runtime quotas use their own matching consumer, build,
instance, replica, rank, admission/stage and accounting definition. A physical
pool total is never divided equally to invent a rank limit.

A vector database can use an explicitly qualified service runtime with its
actual local host/device bindings and a qualified absence of an inference-engine
requirement. Index and temporary maintenance allocations retain separate
lifetimes. An opaque provider service still has unresolved remote capacity.

`CapacityWorkload` evaluates original positive integer `sum(R * E)` for one
actual model-engine/build/instance/replica/rank/admission/stage and operation.
Its class coverage must name that exact operation. Only qualified sequence
admission covering all resident KV in that same domain may reduce the expanded
count. Request and per-step limits cannot silently become resident-sequence caps.
An explicit qualified expanded-demand fallback retains the full count and an
unknown admission result. This consumer does not infer KV bytes, token geometry,
runtime support, service-runtime concurrency policy or context limits.

`CapacityResult.outcome` keeps failure above unresolved checks, then qualified
passes, with explicit inapplicability separate. `conditionalCapacity` classifies
the kind of calculation; it is not a pass or readiness flag. Each check retains
`severity: error` and `onUnknown: review`. A UI must still map these records,
assumptions, unknowns and bounded evidence into the accepted presentation.

## Bounds and validation

The native supporting JSON boundary limits documents to 512 KiB, 48 nesting
levels, 16,384 nodes and 4,096-byte numeric tokens. Direct answer indexes admit
2,048 records, 128 pointer components and 16 KiB pointers. Named basis inputs
are further limited to 256 KiB each, 32 inputs and 2 MiB aggregate. Exact names
are at most 4,096 UTF-8 bytes; Build selection/link limits are 512/1,024.
Normalized ByteCount/count magnitudes admit 4,096 decimal digits; an overflowing
arithmetic result reports the explicit native limit. Memory allows at most 64
scenarios, 4,096 residency rows and 8,192 access rows. Qualifications have a
separate 8,192-entry cap.

Unused decimal/exponent tokens still obey the original finite binary64
shortest-decimal admission rule. Count and byte arithmetic does not use Double
or Int coercion. Exponent, Unicode, depth/size and digit exclusions are explicit
consumer limits, not revisions to canonical wire maxima or general JSON parity.

The new source declares **109 capacity XCTest methods**: five answer-reader,
12 basis/qualification, 24 binding/deployment, 28 memory, 18 worked examples and
22 workload methods. The separate 249-case answer corpus has 125 canonical-reader
positives, 123 selected-field positives and 120 native-profile positives.
`1.0` and `1e0` account for the two reader/selected-field differences; the three
native exclusions are a bounded exponent, 129 pointer components and a 4,097-digit
ByteCount. All original payload hashes, states, attribution and lossless expected
values remain in the corpus. Its SHA-256 is
`36dc22d3a60f55bbbbffe5895937e46b8f11c35909babb86567aa8fe364c1052`
for 175,660 bytes.
